---
description: Plan one version. Produce or update implementation_plan.md and task.md, then wait for the human's approval of that version
---
1. Adopt the `team-lead-orchestrator` skill. Read `requirements.md` and `.agents/rules/nextjs-todo.md`. If `requirements.md` is missing, tell the human to run `/spec` and stop.
2. Decide which version you are planning: the number the human passed (for example `/plan 2`), otherwise the lowest-numbered version whose status line is not `APPROVED`. Say which one you chose.
3. If planning Version 2 or later, first read the real code and `implementation_plan.md` from the earlier versions, and base the new plan on what actually exists. Do not change the sections of earlier versions.
4. Write or update `implementation_plan.md` in the project root. Keep one status line per version at the very top (`Status V1: DRAFT`, `Status V2: DRAFT`, ...). Include the shared foundation (the `Todo` type, validation rules, the full `TodoService` interface, the `src/` folder structure) and a detailed section for the version being planned, with an outline only for later versions. For Version 2 and later that section contains the API table (methods, paths, bodies, status codes, shared error shape), the data model, and the list of files expected to change. Mark every open decision as `OPEN`.
5. Write or update `task.md` in the project root. If it does not exist, start from `.agents/templates/todo-nextjs/task.md`. It starts with `Tracking: local` (unless the human asked for GitHub). Group slices under `# Version <n>: <name>` headings. The first slice of Version 1 is bootstrap. Every later slice is a vertical feature slice with acceptance criteria and a test list. Mark slices the human might not want as `(optional)`.
6. Keep one source of truth. If `task.md` contains a draft contract, data model, or API section (for example one copied from a seed), move anything useful into `implementation_plan.md` and remove that section from `task.md`. `task.md` must contain only checklists, acceptance criteria, and tests.
7. Self-check before presenting: every acceptance criterion is testable, every feature in `requirements.md` for this version is covered by a slice, no slice mixes unrelated features, and for Version 2 and later no slice needs to change a component or hook to swap the backend.
8. Present both artifacts and list the open decisions you need answered. **STOP and wait.** Apply the human's comments, keep the version's status as `DRAFT`, and re-present until they approve.
9. Only when the human explicitly says the plan for that version is approved, change its line to `Status V<n>: APPROVED by human on <YYYY-MM-DD>`. Never write this line on your own initiative, and never treat silence or a comment as approval. If the plan for an approved version changes later, set its status back to `DRAFT` and ask again.
10. Tell the human their options: run `/bootstrap` (Version 1 only) and then `/slice` step by step, or run `/autopilot` to build the whole version hands-off.
